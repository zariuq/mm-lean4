\begin{abstract}
We present a formal verification, carried out entirely in Lean~4 with
the Batteries library (no Mathlib), that the Metamath proof checker
\lean{checkBytes} correctly validates mathematical proofs.
AI assistance: Codex, ChatGPT Pro, and Claude Code (under human supervision).
The central result is completeness and soundness for source text,
against Mario Carneiro's declarative semantics: after any prefix that the
parser reads without error and that ends between statements with no token
pending, in a mode without duplicate \verb|$f| statements, the statement a \verb|$p| claim
would store is provable from the assertions read so far \emph{if and only
if} the parser reads a rendered continuation
(fresh dummy-variable \verb|$v|, \verb|$f| and \verb|$d| statements and one
normal proof) and stores exactly that statement with a complete proof.
The same holds for the complete file checked by \lean{checkBytes}, and
through the entry point \lean{check} for a root file that reads as those
bytes.
A second biconditional relates proof runs in a parsed database to
provability under the Metamath specification (\lean{Spec.Provable}) at the
level of expressions.
Under a strict configuration (\lean{IsSound}), we additionally prove
\emph{prefix provenance}: every accepted theorem is provable using only
earlier theorems, ruling out circular reasoning.
The development comprises about 82{,}000 lines of Lean across 103~files,
with zero \lean{sorry}s and no axioms beyond Lean's standard ones.
All 65 parser error codes are certified to agree with their recorded evidence and specification clause.
The theorems concern source text as the parser reads it
(\S\ref{sec:notclaimed}).
\end{abstract}

\section{Introduction}
\label{sec:intro}

Metamath~\cite{megill2019} is a minimalist proof language used by a
community of formalists to develop large databases of checked theorems,
including \texttt{set.mm} (over 40{,}000 theorems in ZFC set theory).
Its simplicity---constants, variables, substitution, disjoint-variable
constraints, and a stack-based proof checker---makes it an attractive
target for formal verification.

Several implementations of the Metamath proof checker exist, among them
\texttt{metamath.exe} (C), \texttt{mmj2} (Java), \texttt{metamath-knife}
(Rust), \texttt{mmverify.py} (Python), and a Lean~4 verifier by Mario
Carneiro, from which the checker studied here, \lean{checkBytes} in
\file{Verify.lean}, is derived.
They are tested extensively, but none of them is \emph{formally
verified}: proved correct against a mathematical specification.

In this paper we close that gap.  We prove, in Lean~4, that
\lean{checkBytes} is both \emph{sound} (if it accepts a proof,
the theorem is genuinely provable) and \emph{complete} (if the statement
a claim stores is provable, the checker accepts source text that declares
the dummy variables a proof needs and proves it).
These two directions are combined into biconditionals for source text and
for complete files (\S\ref{sec:contract}).

\paragraph{Key results.}
\begin{enumerate}[leftmargin=2em]
\item \textbf{Completeness for source text}:
  in a mode without duplicate \verb|$f| statements, a claim's stored
  statement is provable in Mario's semantics from the assertions read so
  far iff the parser accepts a rendered continuation, or the completed
  file, storing exactly that statement with a complete proof
  (\leansmall{statementProvable_iff_sourceAccepts},
  \leansmall{statementProvable_iff_fileAccepts});
  \leansmall{check_accepts_of_statementProvable} carries this to
  \lean{check}.
\item \textbf{Proof runs}
  (\leansmall{proofChecker_normal_acceptance_iff_specProvable_in_parsedDB}):
  from raw \lean{ByteArray} to \lean{Spec.Provable} at the level of
  expressions, in the default configuration.
\item \textbf{Frame-derivability bridge}
  (\leansmall{proofChecker_normal_iff_frameDerivable_in_parsedDB}):
  the same biconditional bridged to derivability by Mario's rules in
  the frame (\lean{FrameDerivable}) over total database extraction.
\item \textbf{Completeness for Mario's semantics}
  (\leansmall{statementProvable_iff_exists_extendedFrame}):
  a stored statement is provable in Mario's statement-level semantics
  iff some extended frame of it has a Metamath proof.
\item \textbf{Prefix provenance}
  (\leansmall{checkBytes_finalState_finishProofEvent_certified}):
  every accepted \texttt{\$p} theorem is provable in the
  \emph{pre-insertion} database, under a strict configuration.
\item \textbf{Compressed proofs reduce to normal proofs}
  (\lean{ProofReachableZ_iff_NormalProofReachable}):
  every compressed or Z-compressed proof run yields a normal one, at the database level.
\item \textbf{Error code certification}
  (\lean{checkBytes_parseErrorCode?_fullyCertified}):
  all 65 error codes agree with their evidence payload.
\end{enumerate}

\paragraph{Trust boundary.}
The theorems are checked by Lean's kernel.  The core semantic theorems
are stated over \lean{checkBytes} on \lean{ByteArray} input.  The default
IO checker is \lean{check}, which performs single-pass include handling
with bounded depth (\lean{ModeConfig.maxIncludeDepth}) around a pure
parser-step core.  For a single root file, \lean{check} returns what
\lean{checkBytes} returns on the file's bytes, when the include depth
limit is positive, the path resolves, the read returns those bytes, and
the pure run raises no include request (\file{RootFileCheck.lean}).
Source text with include directives is not covered by the completeness
theorems.  The filesystem calls (\lean{realPath}, \lean{readBinFile}) are
trusted, and running the compiled checker also relies on the Lean
compiler and runtime.

\section{Metamath Specification Anchors}
\label{sec:spec}

The Metamath language is defined in Chapter~4 of the Metamath
book~\cite{megill2019}.  We briefly recap the core concepts and their
Lean formalizations.

\subsection{Core Concepts}

A Metamath database declares \emph{constants} (fixed symbols like
\texttt{wff}, \texttt{|-}, \texttt{(}) and \emph{variables} (placeholders
that can be substituted).  An \emph{expression} is a sequence of math
symbols (\S4.2.2); in a hypothesis or an assertion it begins with a
constant, its \emph{typecode}.  Both formalizations below represent such
an expression as a typecode together with the list of the remaining
symbols.  A \emph{substitution} maps variables to expressions.

\emph{Disjoint variable} (DV) constraints (\texttt{\$d} statements)
restrict which variables may share substituted variables---this is the
mechanism that prevents unsound capture.

A \emph{frame} collects the mandatory hypotheses (floating \texttt{\$f}
and essential \texttt{\$e}) and DV constraints for an assertion.
Table~\ref{tab:spec-mapping} shows the correspondence between
specification sections and Lean types.

\subsection{Two Formalizations of Provability}

We maintain two independent formalizations of what it means for a theorem
to be provable:

\paragraph{Operational (\texttt{Spec.Provable}).}
Defined in \file{Spec/Operational.lean}, this models the Metamath proof
checker as a stack machine.  A proof is a sequence of steps; each step
either pushes a hypothesis or applies an assertion (popping arguments
and pushing the conclusion).  A formula is provable if there exists a
step sequence that produces a singleton stack containing it.

\begin{lstlisting}[caption={Operational provability (\file{Spec/Operational.lean}).},label=lst:provable]
def Provable (G : Database) (fr : Frame) (e : Expr) : Prop :=
  exists (steps : List ProofStep) (finalStack : List Expr),
    ProofValid G fr finalStack steps
    and finalStack = [e]
\end{lstlisting}

The \lean{ProofValid} inductive relation (Listing~\ref{lst:proofvalid}
in Appendix~\ref{app:listings}) defines the step-by-step stack machine
execution, with constructors for essential hypotheses, floating
hypotheses, and axiom/theorem application (including DV checking and
type preservation).

\paragraph{Declarative (\texttt{Declarative.Provable}).}
Defined in \file{DeclarativeSpec.lean}, after Mario Carneiro's Lean
specification of Metamath, this is a ``big-step'' inductive with three
constructors: use a hypothesis directly, type any variable, or apply an
axiom with a substitution that satisfies its DV constraints and whose
hypothesis instances and variable typings are all provable.

\begin{lstlisting}[caption={Declarative provability (\file{DeclarativeSpec.lean}).},label=lst:semantic]
inductive Provable (axs : Statement -> Prop) (G : Context)
    : Formula -> Prop
  | hyp (h) : h in G.hyps -> Provable axs G h
  | var (v:VR) : Provable axs G v
  | ax (s) {ax} : axs ax -> ax.ctx.dj.subst s G.dj ->
    (forall h in ax.ctx.hyps, Provable axs G (h.subst s)) ->
    (forall v in ax.vars, Provable axs G (v.type, s v)) ->
    Provable axs G (ax.fmla.subst s)
\end{lstlisting}

The typing premise of the \lean{ax} rule ranges over \lean{ax.vars}, the
variables of the applied statement, as in clause~2(a) of the closure in
Appendix~C.2.5 of the book.  Mario Carneiro's original rule asks for a
typing of every variable; \file{Spec/DeclarativeOriginal.lean} keeps that
rule and proves that the two rules make the same statements provable over
trimmed axiom sets, which include every set of assertions a parsed
database yields (\lean{DeclarativeOriginal.statementProvable_iff},
\lean{dbToAxioms_trimmed}).

The operational and declarative formulations are proven equivalent in
\S\ref{sec:generic}.

\section{The Main Contract}
\label{sec:contract}

The central theorem of the project connects the \emph{actual Lean
implementation} (the parser of \file{Verify.lean}) to Mario Carneiro's
declarative semantics (\file{DeclarativeSpec.lean}) at the level of
source text.

\subsection{Completeness for Source Text}

Let the parser read the text \lean{arr} from the start without error, in a
mode without duplicate \verb|$f| statements, ending between statements
with no token pending.  Take a claim \lean{f} with a constant head and
declared symbols under a fresh label token, whose frame trims to
\lean{frImpl} with stored statement \lean{fr}.

\begin{lstlisting}[caption={Completeness for source text (\file{SourceCompleteness.lean}).},label=lst:source]
theorem statementProvable_iff_sourceAccepts ... :
    (statementOfFrame fr (toExpr f)).Provable
        (dbToAxioms (toDatabaseTotal (afterSource config arr).db))
    <->
    exists ds proof, Admissible (afterSource config arr) ds label f proof
      and SourceAccepts config arr
            (render (afterSource config arr) ds label f proof) label f frImpl
\end{lstlisting}

\lean{render} emits \verb|$v| and \verb|$f| statements for the dummy
variables \lean{ds}, the \verb|$d| pairs the parser stores for them, and
one \verb|$p| statement with the normal proof \lean{proof}.
\lean{Admissible} requires fresh names, legal label and math-symbol
tokens, and proof steps that are label tokens (so no \verb|?| step and no
injected commands).  \lean{SourceAccepts} says that the parser reads the
text after \lean{arr} without error, ends between statements, stores
\lean{label} as exactly \lean{f} with the frame \lean{frImpl}, and records
no new incomplete proof.  Companion theorems show that the declarations
leave the assertion database and the claim's trimmed frame unchanged, and
that the continuation adds exactly the one assertion.
\lean{statementProvable_iff_fileAccepts} states the same for the complete
file, closed by one \verb|$}| per open block and checked by
\lean{checkBytes} with its post-checks, and
\lean{check_accepts_of_statementProvable} with \lean{statementProvable_of_check}
carries it to \lean{check} for a root file that resolves and reads as
exactly those bytes.

The axioms on the left are the assertions read so far: the \verb|$a|
statements and the earlier \verb|$p| statements, including, in modes that
accept \verb|?| steps, theorems whose proofs are incomplete.  Naming
\lean{fr} is no restriction: a frame that trims at such a prefix always
has a spec frame (\lean{exists_toFrame_of_trim}).  For Mario Carneiro's original
\lean{ax} rule, the same is stated by
\leansmall{statementProvable_iff_sourceAccepts_originalRule} and
\leansmall{statementProvable_iff_fileAccepts_originalRule}.

\subsection{Proof Runs in a Parsed Database}

\begin{lstlisting}[caption={Proof runs (\file{KernelCorrectness.lean}).},label=lst:main]
theorem proofChecker_normal_acceptance_iff_specProvable_in_parsedDB
    (bytes : ByteArray)
    (label : String)
    (f : Verify.Formula)
    (h_success : (Verify.checkBytes bytes).error? = none) :
    (exists (proof : Array String) (pr_final : Verify.ProofState)
            (f' : Verify.Formula),
      proof.foldlM (fun pr step =>
        Verify.DB.stepNormal (Verify.checkBytes bytes) pr step)
        <..., label, f, (Verify.checkBytes bytes).frame,
              #[], #[], .normal> =
          Except.ok pr_final
      and pr_final.stack.size = 1
      and pr_final.stack[0]? = some f'
      and toExpr f' = toExpr f)
    <->
    (exists (G : Spec.Database) (fr : Spec.Frame),
      toDatabase (Verify.checkBytes bytes) = some G
      and toFrame (Verify.checkBytes bytes)
            (Verify.checkBytes bytes).frame = some fr
      and Spec.Provable G fr (toExpr f))
\end{lstlisting}

\paragraph{Reading the theorem.}
The left-hand side says: there exists a proof array such that folding
\lean{stepNormal} over it (starting from an initial proof state with
the given label and formula) succeeds, producing a singleton stack
whose top element has the same \lean{toExpr} image as~\lean{f}.
The right-hand side says: the database and frame extracted from
the parser state witness \lean{Spec.Provable} for the \lean{toExpr}
image of~\lean{f}.

The only hypothesis is \lean{h_success}: the parser completed without
error, in the default configuration (\lean{checkBytes bytes}).  It concerns proof
runs, not acceptance: \lean{finishProof} compares the final stack with the
claim literally, while \lean{toExpr} maps the empty formula and
\lean{ERROR} to the same expression.  \lean{verify_impl_complete_exact}
gives the literal final stack.

\subsection{Semantic Bridge}

The biconditional is further bridged to Carneiro's declarative semantics:

\begin{lstlisting}[caption={Semantic bridge (\file{ParserEquivalence.lean}).},label=lst:semantic-bridge]
theorem proofChecker_normal_iff_frameDerivable_in_parsedDB
    (bytes : ByteArray)
    (label : String)
    (f : Verify.Formula)
    (h_success : (Verify.checkBytes bytes).error? = none) :
    (exists (proof : Array String) (pr_final : Verify.ProofState)
            (f' : Verify.Formula),
      proof.foldlM (...) = Except.ok pr_final
      and pr_final.stack.size = 1
      and pr_final.stack[0]? = some f'
      and toExpr f' = toExpr f)
    <->
    (exists (fr : Spec.Frame),
      toFrame (Verify.checkBytes bytes)
            (Verify.checkBytes bytes).frame = some fr
      and FrameDerivable
            (toDatabaseTotal (Verify.checkBytes bytes))
            fr
            (exprToFormula (varMapOfFrame fr) (toExpr f)))
\end{lstlisting}

This is the canonical completeness interface at one fixed frame.
Completeness with respect to Mario's own semantics is stated for
stored statements and extended frames
(\lean{statementProvable_iff_exists_extendedFrame},
\file{Spec/Completeness.lean}).

\subsection{Compressed Proofs Reduce to Normal Proofs}

Metamath supports two proof formats: \emph{normal} (explicit label
sequence) and \emph{compressed} (a compact encoding).  We prove that every
compressed run yields a normal run, so reachability in any format is normal
reachability at the database level:

\begin{lstlisting}[caption={Compressed-to-normal reduction (\file{ParserAnyFormatEquivalence.lean}).},label=lst:mode-equiv]
theorem
    ProofReachableZ_iff_NormalProofReachable
    (db : DB) (label : String) (fmla : Formula) (stack : Array Formula)
    (h_wf : WellFormedDB db)
    (h_size : stack.size = 1) (h_fmla : stack[0]? = some fmla) :
    ProofReachableZ db label fmla stack
    <-> NormalProofReachable db label fmla stack
\end{lstlisting}

A reviewer therefore needs to understand only the normal format to trust
accepted compressed proofs.  We do not construct compressed proofs from normal ones.

\section{The Generic Spec Theorem}
\label{sec:generic}

Underneath the parser-level biconditionals lies a specification-level
equivalence between our operational verifier and Mario's declarative
formulation. This section presents the split as soundness + completeness,
which is the natural structure of the proof.

\paragraph{Soundness (\file{Spec/Equivalence.lean}).}

\begin{lstlisting}[caption={Soundness: operational acceptance implies semantic validity.},label=lst:sound]
theorem operational_to_declarative
    {G : Database} {consts : ConstSet} {fr : Frame} {e : Expr}
    (h_wf : WellFormedDatabaseStrong G consts)
    (h_fr_disjoint : Spec.FrameVarsDisjointConsts consts fr) :
    Provable G fr e ->
    Declarative.Provable (dbToAxioms G) (frameToContext fr)
        (exprToFormula (varMapOfFrame fr) e)
\end{lstlisting}

\paragraph{Completeness at one frame (\file{Spec/Equivalence.lean}).}

\begin{lstlisting}[caption={Completeness: frame derivability implies operational acceptance.},label=lst:complete]
theorem frameDerivable_to_proofValid
    {G : Database} {consts : ConstSet} {fr : Frame} {e : Expr}
    (h_wf : WellFormedDatabaseStrong G consts)
    (h_fr_nodup : FloatVarNoDup fr)
    (h_fr_disjoint : Spec.FrameVarsDisjointConsts consts fr)
    (h_mario : FrameDerivable G fr (exprToFormula (varMapOfFrame fr) e)) :
    Provable G fr e
\end{lstlisting}

\paragraph{The \lean{FrameDerivable} condition.}
Mario's \lean{Provable} relation includes a \lean{var} constructor that
requires no hypothesis: any variable is trivially derivable in an
unbounded context.  The operational verifier, however, works with a
finite frame map and can only accept variables that are explicitly
typed by floating hypotheses.

\lean{FrameDerivable} is \lean{Provable} where every \lean{var} leaf
must be a variable of the frame's floating hypothesis map: derivability
by Metamath's rules in that frame, which is exactly what the verifier
accepts.  It is the instance of \lean{Derivable axs T} (\file{Spec/Derivable.lean}),
Mario's \lean{Provable} with a set \lean{T} of typed variables, which
is the closure of a \emph{pre-statement} in the Metamath book's
Appendix~C.  The book defines a statement to be provable if it is the
reduct of a provable pre-statement;
\lean{Statement.provable_iff_exists_extension} proves that this is
Mario's \lean{Statement.Provable}.  Mario's \lean{Provable} is strictly stronger at one fixed
frame: \file{Spec/FixedFrameCounterexample.lean} gives well-formed
databases in which a statement is provable in Mario's semantics but has
no proof in its own frame, because a dummy variable or an optional
\verb|$d| statement is missing.  The Metamath book (\S4.2.7) lets a proof
use an \emph{extended frame}: the frame plus optional \verb|$f| and
\verb|$d| statements for dummy variables.
\lean{statementProvable_iff_exists_extendedFrame} proves that a stored
statement is provable in Mario's statement-level semantics
(\lean{Statement.Provable}, which uses \lean{Statement.untrim}) iff
some extended frame of it has a Metamath proof.

\paragraph{Premises.}
Both theorems share three structural conditions:
\begin{itemize}[leftmargin=2em]
\item \lean{WellFormedDatabaseStrong}: every assertion in the database
  has well-formed hypotheses, consistent typecodes, and valid DV pairs.
\item \lean{FloatVarNoDup}: floating hypotheses in the frame have
  distinct variables (completeness only).
\item \lean{FrameVarsDisjointConsts}: frame variables do not collide
  with database constants.
\end{itemize}
All three are discharged automatically from parser-success hypotheses
in \file{ParserEquivalence.lean}, so they do not appear as obligations
at call sites.

\paragraph{Stored statements.}
\lean{statementProvable_iff_exists_extendedFrame}
(\file{Spec/Completeness.lean}) combines both directions for stored
statements: soundness through frame trimming
(\lean{statementProvable_of_frameReduction}) and completeness by renaming
the finitely many variables a derivation uses outside the frame into
fresh dummy variables, one \verb|$d| pair per pair of variables involving
a dummy (\lean{exists_dummies_of_statementProvable}).

\paragraph{The checker at a database state.}
At a parser state between statements, the stored statement of a
\verb|$p| claim is provable in Mario's semantics iff, after declaring
finitely many fresh dummy variables with the parser's own \verb|$v|,
\verb|$f| and \verb|$d| actions, the parser accepts a normal-mode proof
of the claim (frame trimming, the proof steps, and \lean{finishProof});
this is \lean{acceptedWithDummies_iff_statementProvable} in
\file{CheckerCompleteness.lean}.  The declarations here are database
actions; \file{SourceCompleteness.lean} realizes them, and the proof, as
source text (\S\ref{sec:contract}).

\paragraph{Bridge functions.}
The equivalence uses four translation functions:
\begin{itemize}[leftmargin=2em]
\item \lean{dbToAxioms}: maps the operational \lean{Database} (a partial function
  from labels to frame--expression pairs) to a predicate on \lean{Statement}s.
\item \lean{frameToContext}: converts an operational \lean{Frame} to a
  declarative \lean{Context} (hypothesis list + DV relation).
\item \lean{exprToFormula}: converts an operational \lean{Expr} to a
  declarative \lean{Formula} (typecode--term pair).
\item \lean{varMapOfFrame}: extracts the variable-to-typecode mapping
  from floating hypotheses in the frame.
\end{itemize}

A reviewer should check that these translations faithfully model the
Metamath specification (\S\S4.1--4.2 of~\cite{megill2019}).

\section{Prefix Provenance}
\label{sec:prefix}

\subsection{The Circularity Problem}

When building a database incrementally (reading a \texttt{.mm} file
top to bottom), each \texttt{\$p} theorem is inserted \emph{after} its
proof is checked.  But can we be sure a theorem doesn't use itself---or
a later theorem---in its own proof?

Under the default Metamath configuration, the answer is \emph{no}:
the \texttt{?}~step mechanism (section 4.4.6 of~\cite{megill2019})
allows incomplete proofs that push the theorem's own formula onto the
stack without any real proof.  This is by design---\texttt{?}~marks
a proof as incomplete---but it means the parser cannot guarantee that
accepted proofs are genuinely sound in the pre-insertion database.

\subsection{The \texttt{IsSound} Predicate}

We define a configuration predicate that is sufficient for prefix
provenance:

\begin{lstlisting}[caption={\lean{IsSound} (\file{Verify.lean}).},label=lst:prefix-cfg]
def IsSound (c : ModeConfig) : Prop :=
  c.rejectUnknownSteps = true
  and c.allowDuplicateFloat = false
\end{lstlisting}

Two concrete configurations satisfy this:
\begin{itemize}[leftmargin=2em]
\item \lean{sound}: minimal strict mode (\lean{rejectUnknownSteps := true}).
\item \lean{knife}: stricter mode (also rejects top-level essential hypotheses).
\end{itemize}

\subsection{The Prefix Provenance Theorem}

\begin{lstlisting}[caption={Prefix provenance (\file{PrefixProvability/Checker.lean}).},label=lst:prefix]
theorem checkBytes_finalState_finishProofEvent_certified
    (arr : ByteArray) (config : ModeConfig)
    (h_cfg : config.IsSound)
    (h_success : (checkBytes arr config).error? = none) :
    let s0 : ParserState := { (default : ParserState) with
      db := { (default : DB) with config := config } }
    forall (pos : Nat) (tk : ByteSlice) (pr : ProofState),
      FinishProofEvent (s0.feedAll 0 arr) pos tk pr ->
      exists (G : Spec.Database) (fr : Spec.Frame),
        toDatabase (s0.feedAll 0 arr).db = some G
        and toFrame (s0.feedAll 0 arr).db
              (s0.feedAll 0 arr).db.frame = some fr
        and Spec.Provable G fr (toExpr pr.fmla)
\end{lstlisting}

\paragraph{Reading the theorem.}
For every \lean{FinishProofEvent} (a moment during parsing when
a \texttt{\$p} proof is completed), the theorem's formula is
\lean{Spec.Provable} in the database and frame at the moment of
the event---\emph{before} the theorem is inserted.  This rules out
circular reasoning.
\lean{check_storedStatements_writtenProof}
(\file{StoredStatementSoundness.lean}) supplies local insertion-event
witnesses for stored assertions in an \lean{IsSound} mode; its conclusion
does not retain membership of those witnesses in the actual run.
\lean{check_every_theorem_provable_from_run_axiom_events}
(\file{RunEmission.lean}) retains the actual-run membership and
\verb|$a|/\verb|$p| classification, and eliminates earlier theorems by cut:
every stored theorem is provable from the run's \verb|$a| statements.

\paragraph{Proof technique: ghost predicates.}
The proof maintains a \lean{ProofGhost} invariant through the parser
loop.  This ghost tracks the proof state's stack and heap certificates,
the preload phase structure (for compressed proofs), and a scope
condition (that the proof frame's hypotheses are a subset of the
database frame).  The ghost is established when a \texttt{\$p} token
starts a proof and maintained through every \lean{feedToken} call.
At \lean{finishProof}, the ghost is discharged to produce
\lean{Spec.Provable}.

\section{What Is Not Claimed}
\label{sec:notclaimed}

Honest verification requires documenting not just what is proved but
also what is \emph{not} proved.

\paragraph{Include expansion.}
The default checker path is single-pass include handling
(\lean{check}) with bounded depth and explicit include errors.
The parser/driver split keeps parser stepping pure and isolates IO in
the include-dispatch loop.  The bridge between \lean{check} and
\lean{checkBytes} is proved for a single root file whose run raises no
include request; completeness for source text with include directives is
not claimed, and the filesystem calls are trusted.

\paragraph{Error codes: consistency only.}
The theorem \leansmall{checkBytes_parseErrorCode?_fullyCertified}
(Listing~\ref{lst:errorcode}, Appendix~\ref{app:listings})
proves that each of the 65~error codes agrees with the evidence the parser
recorded: the evidence has the code's tag and payload shape, and the rule
predicate of the code holds of it.  These predicates
are stated over the recorded evidence, so the theorem certifies the consistency
of each diagnostic; it does not prove, independently of that evidence, that the
source violates the rule.
Nor do we prove that ``if violation $X$ is
the first to occur, the parser produces code~$X$.''
First-violation completeness would require formalizing execution-order
priority among checks---tractable but not essential for correctness
review.

\paragraph{The parser's reading is tested, not proved, book-conformant.}
All theorems concern source text as the parser of \file{Verify.lean}
reads it.  No theorem states that the parser accepts exactly the files
the Metamath book accepts; the specification suite and the reference
differential test it.  In the \texttt{zar}, \texttt{sound} and
\texttt{knife} modes the parser rejects a comment that holds a byte
outside the book's character set (book \S4.1.1) or \verb|$(| or
\verb|$)| inside a token (book \S4.1.2); the \texttt{exe} mode treats
vertical tab as whitespace, as \texttt{metamath.exe} does, and the
\texttt{permissive} mode ignores every comment byte and inner \verb|$(|
until the first standalone \verb|$)|.  Comments do not nest, and an
unterminated comment is rejected in every mode.  All modes intentionally
permit different \verb|$f| types for a variable in separate scopes
(\texttt{test59}), rather than enforce the global-type rule of book
\S4.1.3.  Each stored assertion retains its own frame; an application
still has to satisfy its typing premises.  This is separate from the
mode-dependent policy on simultaneously active duplicate \verb|$f|
declarations.  The book's
character set does not make raw terminal display trustworthy: a carriage
return, which the book allows, can overwrite a displayed line.

\paragraph{Normal proofs, without a size bound.}
The source-level theorems produce a normal proof, and no bound on its
size is claimed: a normal proof can be exponentially longer than a
compressed one.  Compressed proofs are related to normal ones at the
database level by \lean{ProofReachableZ_iff_NormalProofReachable}.

\paragraph{Existence, not a proof generator.}
The completeness theorems are existence statements in \lean{Prop}.  They
do not compute the dummy declarations or the proof.

\paragraph{Provability relative to the prefix.}
The source-level theorems relate a claim to the assertions read so far.
In modes that accept \verb|?| steps, these include earlier theorems
whose proofs are incomplete.  Provability from the \verb|$a| statements
alone is proved for complete runs in \lean{IsSound} modes
(\S\ref{sec:prefix}), not for a source prefix.

\paragraph{Mode boundary.}
The source-level theorems assume a mode without duplicate \verb|$f|
statements, as \S4.1.3 of the book requires.  The \lean{exe} and \lean{permissive}
presets allow such statements and are outside these theorems.

\paragraph{Mode-indexed vacuous predicates.}
Some predicates
(\lean{TokpInv}, \lean{ProofGhost}, etc.)\ use
\texttt{|~\_~=>~True} for modes
where the invariant is intentionally vacuous (e.g.\ \lean{TokpInv} is
only constrained in proof mode).  These are \emph{not} placeholder
theorems or masked \lean{sorry}s---they are deliberate
``this mode imposes no constraint'' defaults.

\paragraph{\texttt{toFrame} returns \texttt{Option}.}
The translation \lean{toFrame : DB -> Frame -> Option Spec.Frame} is
genuinely partial: not every implementation \lean{Frame} corresponds
to a well-formed spec \lean{Frame}.  The main biconditional existentially
quantifies over a successful \lean{toFrame} extraction.

\paragraph{No performance claims.}
Heartbeat budgets and \lean{set_option maxHeartbeats} annotations are
engineering accommodations for Lean's kernel, not mathematical claims.

      |
      v

      (KernelCorrectness.lean)
      |
      v
    proofChecker_normal_iff_frameDerivable_in_parsedDB
      (ParserEquivalence.lean)
      |
      v

      |
      v

      (SourceCompleteness.lean)

\subsection{Theorem Chain}

The proof proceeds through the following chain (all sorry-free):

\begin{enumerate}[leftmargin=2em]
\item \lean{checkBytes} parses bytes and validates \lean{wellFormed?}
  as a final gate.
\item \lean{checkBytes_no_error_wellFormed?}: no error implies
  \lean{wellFormed? = true}.
\item \lean{wellFormedDB_of_wellFormed?}: \lean{wellFormed? = true}
  implies \lean{WellFormedDB}.
\item \lean{parser_construction_wellformed}: composes steps 2 and 3.
\item \lean{verify_impl_sound}: the soundness direction
  (a successful proof run implies provability).
\item \lean{verify_impl_complete}: the completeness direction
  (provability implies a proof run whose final formula has the claim's
  expression; \lean{verify_impl_complete_exact} gives the literal final
  stack that \lean{finishProof} requires).
\item \lean{operational_to_declarative}: unconditional spec-level soundness.
\item \lean{frameDerivable_to_proofValid}: completeness from frame
  derivability.
\item \lean{proofChecker_normal_iff_frameDerivable_in_parsedDB}:
  parser-level frame-derivability biconditional.
\item The end-to-end biconditionals: combined from steps 5--8.
\item \lean{statementProvable_iff_exists_extendedFrame}: completeness for
  Mario's semantics, up to extended frames.
\item \lean{acceptedWithDummies_iff_statementProvable}: the same against
  the parser's acceptance at a database state between statements.
\item \lean{statementProvable_iff_sourceAccepts}: the same for the source
  text the parser reads; \lean{statementProvable_iff_fileAccepts} for the
  complete file under \lean{checkBytes}.
\end{enumerate}

\subsection{Key Proof Techniques}

\paragraph{Parser loop induction.}
The main soundness proof uses induction over the token stream,
maintaining a \lean{ParserStateInv} invariant that tracks
well-formedness, frame scoping, and hypothesis consistency.

\paragraph{Ghost predicates.}
For prefix provenance, a \lean{ProofGhost} predicate is maintained
through the parser loop.  The ghost carries four conjuncts tracking
stack/heap certificates, the preload phase structure, and the scope
condition for compressed proofs.

\section{Conclusion}
\label{sec:conclusion}

We have presented a formal verification of a Metamath proof checker
against Mario Carneiro's declarative semantics.  The central
result---completeness and soundness for source text, also for complete
files under \lean{checkBytes} and root files under \lean{check}---establishes
that the implementation is sound and complete for source text as its
parser reads it, with normal proofs as witnesses, in modes without
duplicate \verb|$f| statements.  Proof runs in a parsed database are
related to specification-level provability, and under strict
configuration, prefix provenance rules out circular reasoning.

\paragraph{Related work.}
\texttt{metamath.exe}, \texttt{mmj2}, \texttt{metamath-knife} and
\texttt{mmverify.py} are checked against shared test suites rather than
proved correct; the differential harness of this project compares the
verdicts of its \texttt{exe} and \texttt{knife} modes with those of
\texttt{metamath.exe} and \texttt{metamath-knife}.  Metamath
Zero~\cite{carneiro2019mm0} is a related verification system designed
with the goal of a verifier whose own correctness is proved.
The Metamath specification~\cite{megill2019} defines the proof system
but does not itself come with a machine-checked proof of checker
correctness.

\paragraph{Future directions.}
Three natural extensions remain:
\begin{itemize}[leftmargin=2em]
\item Error code \emph{completeness}: proving that if a specific
  violation occurs first, the parser produces the corresponding code.
\item A filesystem-oracle model for IO dispatch (\lean{realPath},
  \lean{readBinFile}), and completeness for source text with include
  directives.
\item Integration with mm0: bridging our Lean formalization to
  the mm0 proof format used by \texttt{mm0-rs}.
\end{itemize}

\subsection{\texttt{Spec.ProofValid} (\file{Spec/Operational.lean})}

\begin{lstlisting}[label=lst:proofvalid]
inductive ProofValid (G : Database) :
    Frame -> List Expr -> List ProofStep -> Prop where
  | nil : forall fr, ProofValid G fr [] []
  | useEssential : forall fr stack steps e,
      Hyp.essential e in fr.hyps ->
      ProofValid G fr stack steps ->
      ProofValid G fr (e :: stack)
        (ProofStep.useHyp (Hyp.essential e) :: steps)
  | useFloating : forall fr stack steps c v,
      Hyp.floating c v in fr.hyps ->
      ProofValid G fr stack steps ->
      ProofValid G fr (<c, [v.v]> :: stack)
        (ProofStep.useHyp (Hyp.floating c v) :: steps)
  | useAxiom : forall fr stack steps l fr' e s,
      G l = some (fr', e) ->
      dvOK fr.vars fr'.dv fr.dv s ->
      (forall c v, Hyp.floating c v in fr'.hyps ->
        (s v).typecode = c) ->
      ProofValid G fr stack steps ->
      forall needed : List Expr,
      needed = fr'.hyps.map (fun h => match h with
        | Hyp.essential e => applySubst fr'.vars s e
        | Hyp.floating _ v => s v) ->
      forall remaining : List Expr,
      stack = needed.reverse ++ remaining ->
      ProofValid G fr (applySubst fr'.vars s e :: remaining)
        (ProofStep.useAssertion l s :: steps)
\end{lstlisting}
